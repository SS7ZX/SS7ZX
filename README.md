## How I Approach Engineering

A few principles that shape how I build and how I test, laid out plainly so a hiring manager knows what working with me actually looks like day to day.

**I build before I theorize.** I would rather have a working prototype with rough edges than a perfect plan that never ships. Most of my learning has come from finishing things and then going back to fix what broke.

**I test my own work like an outsider would.** Once a feature works, my next question is always "how would someone abuse this." That single habit has caught more bugs in my own code than any external review has, simply because it happens earlier and more often.

**I document as I go, not after.** Every project in this README has notes written during development, not reconstructed afterward. This matters for handoffs and for anyone reviewing my work later, including future me.

**I prefer boring, auditable solutions over clever ones.** In the C-Pay case study below, you will see that transaction logic is deliberately isolated into a single code path. That decision cost some flexibility but bought a lot of confidence that balances cannot drift silently.

**I ask for feedback early and often.** On the Bhaswara competition project, working as part of a team meant learning to take direction on product decisions I did not originally propose, and that experience shaped how I think about compromise in a team setting.

**I am comfortable saying "I do not know yet."** Go, Supabase Edge Functions, and formal bug bounty methodology are all things I am actively learning rather than things I have mastered. I would rather flag that clearly than let it surface awkwardly later.

## Security Methodology

My approach to VAPT and application security work follows a repeatable five-step process, developed through both the university-recognized assessment and the self-built pentesting lab described below.

```
1. RECON          2. MAPPING              3. EXPLOITATION           4. VALIDATION            5. REPORT
   Subfinder,         Attack surface           IDOR, auth bypass,        Confirm real,            Findings plus
   Amass, Gau         and endpoint             OWASP Top 10 checks       reproducible impact,      mitigation
                       enumeration                                        not false positives       guidance
```

### 1. Recon

Enumerate subdomains, live hosts, and historical endpoints using subfinder, amass, gau, and waybackurls to build a full picture of the target's attack surface before any manual testing. The goal at this stage is coverage, not depth. I would rather miss nothing and prioritize later than start deep on one endpoint and miss an easier path elsewhere.

### 2. Mapping

Walk the mapped surface to understand application logic: authentication flows, role boundaries, API structure, and where user-controlled input meets business logic. This is where I build a mental model of the application as if I were the developer, since understanding intended behavior is the fastest way to spot where it breaks.

### 3. Exploitation

Focused manual testing against high-risk classes, primarily IDOR (does changing an identifier expose another user's data) and authentication bypass (can protected routes be reached without a valid session), alongside the broader OWASP Top 10. I prioritize access control issues because in my experience they tend to have the clearest, most demonstrable impact.

### 4. Validation

Every finding is retested to confirm real, reproducible impact. Theoretical or unconfirmed issues are not included in a final report. This step exists because a report full of unconfirmed findings wastes a development team's time and erodes trust in future reports.

### 5. Report

Findings are documented with clear reproduction steps and concrete mitigation guidance, written so a developer, not only a security team, can act on them directly. I include a severity rationale, not just a severity label, so the reader understands why something matters and not just that it does.

### Why this order matters

Skipping recon and jumping straight to exploitation is the most common mistake I see in early-career security work, myself included when I started. A narrow view of the attack surface means missing the actual weak point in favor of the first thing that looked interesting. This methodology was directly responsible for the VAPT Excellence Award from Universitas Siber Indonesia, awarded for a security evaluation of live university digital assets.

## Case Study: C-Pay Architecture

A closer look at how C-Pay, my solo-built closed-loop payment system, is structured, including the reasoning behind key decisions and what I would do differently with more experience.

### The problem

Campus events at my university handled payments with cash, which created two recurring issues: reconciliation errors at the end of each event, and no audit trail when disputes came up about what a student had or had not paid. I built C-Pay to replace that with a closed-loop digital wallet system specific to campus events.

### System architecture

```
+----------------------------------------------------------------------+
|                            CLIENT (React)                            |
|   Event Check-in UI  ·  Wallet Balance View  ·  Merchant Terminal UI |
+-------------------------------------+----------------------------------+
                                       | HTTPS / REST
+-------------------------------------v----------------------------------+
|                     API LAYER (Express.js / Node.js)                  |
|  +----------------+  +-----------------+  +----------------------------+ |
|  | Auth Middleware |  | Transaction     |  | Input Validation and      | |
|  | (session/token) |  | Controller      |  | Sanitization Layer        | |
|  +----------------+  +-----------------+  +----------------------------+ |
+-------------------------------------+----------------------------------+
                                       |
+-------------------------------------v----------------------------------+
|                          DATABASE (MongoDB)                           |
|   Users/Wallets Collection  ·  Transactions Ledger  ·  Event Records  |
+--------------------------------------------------------------------------+
```

### Design decisions and the reasoning behind them

**Transaction logic isolated from the controller layer.** Balance changes can only happen through one audited code path. This was a deliberate constraint: even if a new route or feature gets added later, it has to go through the same transaction function, which means the same validation and logging apply every time. The cost is some development speed, since a quick balance tweak cannot bypass the transaction layer for convenience. I decided that trade-off was worth it for a system handling money.

**Every mutating request re-validates ownership server-side.** This was a direct response to how easily IDOR bugs slip into naive "user owns this record" checks, especially checks that only happen client-side or that trust a request parameter without verifying it against the authenticated session.

**MongoDB chosen for flexible event and transaction schemas.** Campus events have varying metadata needs (different fee structures, different vendor setups, different check-in requirements), and a document model avoided constant schema migrations mid-build. In hindsight, a hybrid approach with PostgreSQL for the transaction ledger specifically might have given stronger consistency guarantees, and that is a change I would consider in a rebuild.

**Authentication used session-based tokens rather than pure JWT.** This was chosen mainly for simpler revocation during the event itself, since being able to kill a session immediately if a device was lost mattered more than the statelessness benefits of JWT for this specific use case.

### What I would do differently

With more experience, I would add automated integration tests around the transaction controller specifically, since that is the highest-consequence code path in the system and it currently relies on manual testing before each deployment. I would also add rate limiting on the transaction endpoints, which was not implemented in the first version and represents a real gap I am aware of.

### Honest scope note

C-Pay was built and used for campus events, not deployed as a commercial payment processor and not handling real-world transaction volume at scale. I want that clearly understood rather than implied otherwise. What it demonstrates is the ability to own a complete system, including the security-conscious decisions above, from schema to shipped product.

### Ownership-checked, fail-closed middleware

```javascript
// middleware/verifyOwnership.js
// Pattern used across C-Pay to prevent IDOR on wallet and transaction routes

const verifyOwnership = (Model, paramField = 'id') => {
  return async (req, res, next) => {
    try {
      const resource = await Model.findById(req.params[paramField]);

      if (!resource) {
        return res.status(404).json({ error: 'Resource not found' });
      }

      // Fail closed: only the authenticated owner may proceed
      if (resource.userId.toString() !== req.user.id.toString()) {
        return res.status(403).json({ error: 'Forbidden' });
      }

      req.resource = resource;
      next();
    } catch (err) {
      next(err);
    }
  };
};

module.exports = verifyOwnership;
```

### The transaction controller pattern

```javascript
// controllers/transactionController.js
// All balance mutations go through this single, auditable function

const applyTransaction = async ({ walletId, amount, type, session }) => {
  const wallet = await Wallet.findById(walletId).session(session);

  if (type === 'debit' && wallet.balance < amount) {
    throw new Error('Insufficient balance');
  }

  wallet.balance = type === 'debit'
    ? wallet.balance - amount
    : wallet.balance + amount;

  await wallet.save({ session });

  await Transaction.create([{
    walletId,
    amount,
    type,
    balanceAfter: wallet.balance,
    timestamp: new Date(),
  }], { session });

  return wallet.balance;
};

exports.create = async (req, res, next) => {
  const dbSession = await mongoose.startSession();
  try {
    dbSession.startTransaction();
    const newBalance = await applyTransaction({
      walletId: req.params.id,
      amount: req.body.amount,
      type: req.body.type,
      session: dbSession,
    });
    await dbSession.commitTransaction();
    res.status(200).json({ balance: newBalance });
  } catch (err) {
    await dbSession.abortTransaction();
    next(err);
  } finally {
    dbSession.endSession();
  }
};
```

### A simple recon script, representative of the Go toolkit in progress

```go
// main.go
// Early-stage subdomain enumeration wrapper, part of the Recon Automation Toolkit

package main

import (
	"bufio"
	"fmt"
	"os"
	"os/exec"
)

func runSubfinder(domain string) ([]string, error) {
	cmd := exec.Command("subfinder", "-d", domain, "-silent")
	output, err := cmd.Output()
	if err != nil {
		return nil, err
	}

	var subdomains []string
	scanner := bufio.NewScanner(bufio.NewReader(os.Stdin))
	for scanner.Scan() {
		subdomains = append(subdomains, scanner.Text())
	}
	_ = output
	return subdomains, nil
}

func main() {
	if len(os.Args) < 2 {
		fmt.Println("usage: recon-tool <domain>")
		os.Exit(1)
	}

	domain := os.Args[1]
	results, err := runSubfinder(domain)
	if err != nil {
		fmt.Println("error running subfinder:", err)
		os.Exit(1)
	}

	for _, sub := range results {
		fmt.Println(sub)
	}
}
```

## FAQ

**Are you a developer who does security, or a security researcher who codes?**

Both, by design. Building full-stack applications means I see firsthand where developers cut corners, which sharpens the security work. Doing security work means I write code that is harder to break in the first place. I do not think of these as two resumes stitched together, they genuinely inform each other on every project.

**What kind of role are you looking for?**

Full-stack development, junior red team or cybersecurity, or a hybrid role that values both. Open to internship or entry-level full-time positions, remote, hybrid, or onsite in the Jakarta area.

**Do you take freelance security review work?**

Yes. Reach out by email or LinkedIn with project scope and timeline, and I will let you know honestly whether it is within what I can currently deliver well.

**What is the story behind C-Pay?**

It started as a way to fix a real problem with campus events, where cash handling was messy and error-prone, and became a project where I owned the full stack: schema, backend, security, and frontend. The full breakdown, including what I would change with more experience, is in the case study section above.

**What is your current experience level, honestly?**

I am a 5th-semester undergraduate. My projects are self-directed and internship-based rather than large-scale production systems, and I frame them that way intentionally throughout this README. What I can offer is strong fundamentals, a security-first habit formed early, and a track record of finishing what I start and being transparent about the gaps.

**What are you not good at yet?**

Automated testing infrastructure, large-scale cloud security, mobile app security, and formal bug bounty methodology are all areas I am actively working on rather than areas of strength today. I would rather list that clearly than have it come up as a surprise in an interview.

**How do you prefer to be contacted?**

Email or LinkedIn, both linked at the top of this README and again in the contact section below. I typically respond within 48 hours.
